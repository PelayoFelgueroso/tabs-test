## 🎯 Core Design Decisions

### 1️⃣ **Controlled-First API with Uncontrolled Sugar**

```typescript
// Professional apps need controlled state
const [tab, setTab] = useState("home");
<Tabs value={tab} onChange={setTab} variant="pill">
  <Tabs.Tab value="home" label="Home">Content</Tabs.Tab>
  <Tabs.Tab value="settings" label="Settings">Settings</Tabs.Tab>
</Tabs>

// Simple cases don’t need boilerplate
<Tabs defaultValue="home">
  <Tabs.Tab label="Home">Content</Tabs.Tab>
</Tabs>
```

**Why this matters:**
- **URL syncing**: `<Tabs value={new URLSearchParams().get("tab")} onChange={...} />`
- **Undo/Redo**: Parent controls state → history integration
- **Server state**: Match server-side tab selection
- **Analytics**: Log every tab change via `onChange`

---

### 2️⃣ **Value vs Label Separation**

```typescript
<Tabs.Tab 
  value="settings"              // Identifier: URL-safe, stable
  label="⚙️ Settings"           // Display: can change, supports i18n
/>
```

**Why this matters:**
- **i18n**: `label="Settings"` → `label="Ajustes"` (value stays `"settings"`)
- **URL slugs**: `<Tabs value={slug} />` → route to `/settings`
- **Semantic clarity**: "What is it called?" vs "How do we reference it?"
- **Test readability**: `getByRole("tab", { name: "Settings" })` finds the tab

---

### 3️⃣ **Roving Tabindex Keyboard Pattern (WAI-ARIA Standard)**

```
User presses...        Behavior
─────────────────────────────────────────────
← or →                 Move focus between tabs (don’t activate)
↑ or ↓                 Move focus between tabs (don’t activate)
Home                   Jump to first tab
End                    Jump to last tab
Enter or Space         Activate focused tab
```

**Why this pattern:**
- ✅ **Explore without committing**: Users can preview tabs before activating
- ✅ **Power user friendly**: Arrow keys are faster than click-based navigation
- ✅ **Mobile accessible**: Focus and activation are separate concerns
- ✅ **Standard compliance**: Matches [WAI-ARIA Tab Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)

---

### 4️⃣ **Explicit TabPanel Structure with ARIA Semantics**

```typescript
// Tab element
<button
  id="tab-settings"
  role="tab"
  aria-selected={isActive}
  aria-controls="tabpanel-settings"
>
  Settings
</button>

// Panel element
<div
  id="tabpanel-settings"
  role="tabpanel"
  aria-labelledby="tab-settings"
  hidden={!isActive}
>
  Panel content
</div>
```

**Why this structure:**
- **WCAG 1.3.1**: Info and Relationships → Screen readers understand structure
- **WCAG 4.1.2**: Name, Role, Value → Assistive tech announces state
- **`hidden` attribute**: Removes inactive panels from a11y tree (cleaner for VoiceOver/NVDA)
- **aria-labelledby**: Connects panel to its controlling tab

---

### 5️⃣ **Context API for Compound Components**

```typescript
<Tabs variant="pill">
  <Tabs.Tab label="One">Content 1</Tabs.Tab>  // ← Consumes context
  <Tabs.Tab label="Two">Content 2</Tabs.Tab>  // ← No prop drilling
</Tabs>
```

**Why this approach:**
- **No prop drilling**: `<Tab>` doesn’t need `variant`, `activeTab`, `setActiveTab` as props
- **Clean API**: Mirrors React idioms (`<Suspense>`, `<StrictMode>`)
- **Extensible**: Add features (disabled state, loading) without API bloat
- **Type-safe**: Context type ensures correct usage

---

### 6️⃣ **Two Variants: Pill & Underline**

| Variant | Best For | Visual Style |
|---------|----------|--------------|
| **Pill** (default) | App UIs, dashboards | Rounded buttons with background |
| **Underline** | Documentation, content | Minimal underline indicator |

Both are **design tokens**, not hard-coded:
```scss
// Change tokens, change the component
--tab-bg-default: #f5f5f5;       // Pill background
--tab-underline-color: #000000;  // Underline color
--tab-height-mobile: 40px;       // Scale for mobile
```

---

### 7️⃣ **Design Token Architecture (3 Layers)**

```
PRIMITIVES (Foundation)
  color-gray-900, color-success, color-error
  spacing-xs, spacing-sm, spacing-md, spacing-lg, spacing-xl, ...
  font-size-sm, font-size-md, font-size-lg
  line-height-tight, line-height-normal, line-height-loose
  border-radius-sm, border-radius-md, border-radius-full

SEMANTICS (Context-aware)
  bg-default, bg-hover, bg-active, bg-selected
  text-primary, text-secondary, text-on-primary
  border-default, border-hover, border-active
  state-hover, state-active, state-disabled

COMPONENTS (Specific)
  --tab-height, --tab-height-md
  --tab-bg-selected, --tab-text-selected
  --tab-padding-inline-mobile, --tab-padding-inline-desktop
  --badge-padding-block, --badge-border-radius
```

**Why three layers?**
- **Consistency**: Primitives define the design language (colors, spacing, typography)
- **Flexibility**: Semantics adapt to context (light/dark mode, brand themes)
- **Maintainability**: Components encapsulate their own styling
- **Scalability**: New colors/spacing added at primitives → available everywhere

---

### 8️⃣ **Badge Integration via Tab Props**

```typescript
<Tabs.Tab 
  label="Notifications" 
  badge={{ 
    label: "5", 
    variant: "positive"  // "neutral" | "positive" | "negative"
  }}
>
  Content
</Tabs.Tab>
```

**Why this design:**
- **Semantic**: Badge is metadata about the tab, not content
- **Simple**: No child complexity, no render props
- **Positioned**: Component handles layout and spacing
- **Extensible**: Easy to add badge variants (icon, color, animation)

## 💡 The Philosophy

> **Simplicity ≠ Inflexibility**

This component proves that accessibility and flexibility don’t require complexity. By separating concerns:
- **Control patterns** (controlled vs uncontrolled) adapt to app needs
- **Keyboard behavior** (roving tabindex) follows standards
- **ARIA structure** (tab + panel linking) enables screen readers
- **Styling** (design tokens) scales across light/dark and brand themes

The result: **80% of use cases** are simple and straightforward. **20% of advanced cases** have room to grow without API redesigns.

This is production design system thinking.
